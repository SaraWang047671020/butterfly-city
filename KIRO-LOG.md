# Kiro Log

A running record of where I got stuck and which Kiro feature got me unstuck. One row per problem. The Evidence column points to files or commits in this repository.

| Date | Problem | Kiro feature used | Result | Evidence |
|---|---|---|---|---|
| 2026-11-11 | Starting a data-heavy simulation alone. I needed every later session to follow the same rules (pure engine, cited parameters, political neutrality) without repeating them in each prompt. | **Steering**: generated from a written project brief. Three always-on files (`product.md`, `tech.md`, `structure.md`), `neutrality.md` set to `inclusion: always`, and `simulation.md` set to `inclusion: fileMatch` so the model invariants load only when working in `src/simulation/**`. | Five steering files that every later spec cites. The neutrality rules appear in specs without being asked for again. | `.kiro/steering/`, commit `580822e` |
| 2026-11-11 | I did not know whether open data for 41 districts over 2015–2025 really existed. Descriptions on the data portal are often wrong or incomplete. | **Agent chat** (no spec): asked Kiro to download every candidate source and count records per district and quarter, rather than read descriptions. | 9 sources checked by actual download. Found gaps I would have missed: a 20–30% income series break in 2019, 3 rural districts with zero rental records, MRT hourly files totalling about 35 GB, a missing 2015 Q1–2016 Q2 affordability series. Each gap got a written decision. | `data/DATA-CHECK.md` |
| 2026-11-11 | The data pipeline has many edge cases (late registrations, thin districts, series breaks). I needed them written down before any code. | **Spec** (`/spec new` in the CLI, Feature, Requirements first). | `data-pipeline` requirements with 18 requirements in EARS format, each data gap from DATA-CHECK mapped to a requirement. | `.kiro/specs/data-pipeline/requirements.md` |
| 2026-11-11 | Requirements written in natural language can be read two ways, and I could not see where. | **Analyze requirements** (`/spec analyze_requirements`). | Kiro found 5 ambiguous criteria (11.7, 9.2, 8.9, 18.7, 16.8). I resolved every one toward the stricter reading: each check holds independently, the wrong CPI series stops the build, an unfillable cell stops the build, tests only count when actually run, and a failed write restores the previous files. | `.kiro/specs/data-pipeline/requirements.md` |
| 2026-11-11 | I wanted the design to be testable, not only described. | **Spec design phase** with correctness properties. | Design with 30 correctness properties for property-based testing, transactional output writing (temp files, then rename, roll back on failure), and a documented fallback for thin rural districts. | `.kiro/specs/data-pipeline/design.md` |
| 2026-11-11 | Running tests by hand after each task is easy to forget, and a forgotten run looks like a pass. | **Agent hook** with the `PostTaskExec` trigger. | After every spec task, Kiro runs `npm test` once and reports failures (file, test, expected vs received) without trying to fix them. | `.kiro/hooks/test-after-spec-task.json` |
| 2026-11-11 | The simulation engine is the core of the project and the easiest place to be wrong without noticing. | **Spec** for `simulation-engine` (requirements first), steered by `simulation.md`. | Requirements built around the zero-delta identity: if the player changes nothing, every output equals real history. | `.kiro/specs/simulation-engine/requirements.md` |
| 2026-11-16 | After reviewing realism, I found three problems: 8 tools were too many to source well, real events would be counted twice (their effect is already in the real baseline), and unlimited policy changes push the model far outside where it is valid. | **Spec iteration**: committed the drafts first, then asked Kiro to edit only the affected sections of steering and both specs instead of rewriting them. | Scope narrowed from 8 to 5 housing-focused tools. New rules: events may only scale a policy difference and never move an indicator on their own; every tool has cited limits (default 0–2× real) inside the real budget; contested parameters run at low, central and high, and the UI shows a range. New requirements: a real policy track for the 5 tools, and a backtest against a real policy change with tolerances fixed before the result is computed. 4 new invariants added to the property tests. | Commit `905e473` (before) and the following commit (after); `git diff` on `.kiro/` |
